# D-M1 semantic review

## 1. Verdict

**D-M1 — SINGLE MINIMAL SEMANTIC CLARIFICATION RECOMMENDED**

The existing architecture does not close the gap. The creator is permitted, but not required, to retain the ordinary `database.control` lock across the final rename. Consequently, an independent opener can currently acquire ownership after step 7 and before step 8.

The recommended rule is:

> Root publication owns the ordinary process-local database claim and `database.control` lock from immediately before final-root rename until external-parent durability is established. No ordinary admission, acknowledged database work, or removal authority may pass that gate. Because process death releases the runtime lock and no persisted publication marker exists, the next independent owner of a surviving final root must synchronize and verify its external-parent entry before inspecting database contents, recovering, removing, reaching READY, or acknowledging work.

This is one integrated publication/adoption rule using existing ownership and durability primitives.

## 3–5. Visible-but-not-durable interval

The analytical interval is:

> **VISIBLE-BUT-NOT-DURABLE ROOT INTERVAL:** successful completion of step 7 until successful completion of step 8.

This is not a proposed lifecycle state.

During the interval:

- `D` is visible as the final directory name.
- `D/database.control`, the bootstrap files, system relation files, and `wal/` are reachable under final names.
- The staged contents have been fully synchronized and validated.
- The external-parent entry naming `D` has not been made durable.
- A machine crash may leave the final name, the staging name, or neither, as explicitly allowed by §4.7.8.
- The creator’s retained root-directory descriptor remains attached to the same directory inode.
- Any retained control descriptor remains attached to the same `database.control` inode.
- Persistent FileIds and bootstrap identities are unchanged.
- Only the textual pathname changes.

## 6. Current creator lock ownership

The architecture does **not** require the creator to hold the ordinary owner lock.

[§3.3.7](/home/yghtso/Projects/DBlusBlus/docs/ARCHITECTURE.md:622) says the creator:

> “may retain safely opened root/control descriptors and a lock established on the same control inode across the final rename…”

`MAY` permits this optimization for a returned handle; it does not establish:

- a mandatory acquisition point;
- mandatory same-process registration;
- mandatory retention through the parent `fsync`;
- mandatory ownership for no-handle creation.

## 7–10. Competing actors and dangerous work

| Actor | Current result during interval |
|---|---|
| Another process calls `OpenDatabase(D)` | Can open the final directory and control file. If the creator did not take the optional lock, it can acquire the lock and continue. |
| Same process calls another open | No mandatory creator registry claim exists. It can potentially claim the stable root/control identity and continue. If the creator did establish an equivalent claim, it receives `DATABASE_BUSY`. |
| Database remover | D-M2’s full algorithm is unresolved, but the present D-M1 rules do not prevent it from acquiring the same lock because the creator need not hold it. |
| Second `CreateDatabase(D)` | Already excluded: before rename the staging name collides; after rename final `D` exists and no-replace/absent-root rules reject it. |
| Creator returns an open handle | Current §3.3.7 orders normal ownership/recovery/READY gates after durable root publication; early admission is not authorized. |
| Creator crashes | Any optional lock is released. A runtime-visible final root may remain although parent durability is uncertain. |
| Admitted competing owner crashes | Its database work may be internally durable while the external final-root name remains non-durable. |

The dangerous scenario is permitted by the current text:

1. Creator completes final-root rename.
2. External-parent `fsync` has not succeeded.
3. Creator has not taken the optional owner lock.
4. Independent opener opens final `D`.
5. It acquires the control lock.
6. It validates, recovers, and reaches READY.
7. A transaction reaches durable COMMIT and is acknowledged.
8. The machine crashes before external-parent durability is established.
9. The final root name may disappear.

The root contains durable work, but the namespace path needed to reach that work was not durably published.

## 11. Appendix-B invariant assessment

[Appendix B invariant 13](/home/yghtso/Projects/DBlusBlus/docs/ARCHITECTURE.md:24814) states exactly:

> “Acknowledged durable state never depends on a file or WAL-segment namespace entry whose required parent-directory synchronization has not succeeded.”

D-M1 can violate this because acknowledged control, WAL, status, and data-file state remains reachable only through the unsynchronized external-parent entry naming `D`.

Invariant 18 reinforces the ownership side:

> “One actual database root has at most one process-local owner and one OS-exclusive process owner; recovery and ordinary mutation never run without that ownership.”

Catalog invariant §16.11.18 independently confirms that database creation is not durable until the external parent has been synchronized.

## 12–14. Identity and lock continuity

### Root and control identity across rename

The same-filesystem directory rename changes the basename, not the root-directory inode. The child `database.control` is not independently replaced; it remains the same control inode under the renamed directory.

Stable across rename:

- root-directory inode;
- control-file inode;
- retained root/control descriptors;
- persistent FileIds;
- bootstrap/catalog identities.

Changed:

- textual root pathname;
- staging-versus-final namespace classification.

### Control-lock continuity

The architecture defines the lock as process-associated state on the control inode. It also states in §4.7.4 that an open descriptor continues to identify the same inode across rename.

Therefore, a lock acquired through the staged control descriptor naturally remains attached to the final root’s control inode. A final-path opener reaches that same inode and contends on the same lock.

No new lock file or primitive is needed.

### Same-process claim

The existing registry uses stable actual root/control inode identity, not path strings. Those inodes already exist and are stable before rename.

A future clarification can establish the creator’s publication claim using that same inode pair before rename. It does not need a synthetic pathname identity. The claim must continue across rename and, for a returned handle, into the single resulting `DatabaseInstance`.

## 15. Create-success boundary

Creation success requires successful external-parent `fsync` at step 8; step 9 alone reports that result.

This is explicit in §4.7.8 and §16.9.5. The recommendation does not change this boundary.

## 16. Returned-handle case

The returned-handle path should use continuous ownership:

1. Complete and validate staging bootstrap.
2. Establish the process-local inode claim and ordinary control lock.
3. Rename to the final root.
4. Synchronize the external parent.
5. Continue the same claim, descriptor, and lock into normal open/recovery/READY gates.
6. Return the handle only after READY.

A process-local handle object may be under construction earlier, but it must not be published as READY, admit transactions, or acknowledge work before parent durability.

Releasing and reacquiring the lock would create an unnecessary ownership race and should not be permitted.

## 17. No-handle case

For creation returning only a durable-create result:

```text
successful external-parent fsync
    ->
release the control lock while retaining the local claim
    ->
remove the local claim
    ->
return CreateDatabase success
```

The essential requirements are:

- ownership is not released before parent durability;
- success is not returned before durability;
- no independent opener can enter during the publication interval.

## 18. Parent-fsync failure

Current semantics correctly prohibit creation success, but do not define the gate lifetime.

Under the recommendation:

- the creator retains the ordinary lock and process claim;
- no handle reaches READY;
- no ordinary admission or removal authority proceeds;
- the creator may retry or reconcile the exact namespace outcome;
- it may cleanly release ownership only after either durability is established or a separately valid durable reconciliation removes the final root as an admission target;
- uncertain or unquiesceable `DatabaseInstance` state follows existing failed-open/NONCONTINUABLE rules;
- if the process terminates, the next owner must establish external-parent durability before use.

An `fsync` failure does not prove that the rename persisted or failed to persist.

## 19–21. Creator crash cases

### Before rename

- Final `D` does not exist.
- A staging root may survive.
- Staging is never an `OpenDatabase` target.
- Explicit create/maintenance logic may remove it only after proving no live creator owns it.

No D-M1 change is needed.

### After rename, before parent fsync

Machine-crash classification remains as currently defined: final, staging, or neither may survive; a final survivor must pass complete bootstrap validation.

For process death without machine restart, the final name can remain runtime-visible while still not known durable. Validation alone does not make the external-parent entry durable. Therefore, a subsequent owner must synchronize and verify the external parent before database inspection or admission.

### After parent fsync

The final root is durably published. Process death releases the lock, and ordinary open/recovery applies. Repeating an external-parent sync during a later independent open is conservative but harmless.

## 23. Candidate A assessment

Candidate A is the correct live-owner mechanism:

- `database.control` exists before step 6.
- The creator can acquire its ordinary lock after complete bootstrap validation and before step 7.
- Directory rename preserves the locked inode.
- Final-path openers contend on the same inode.
- The creator can retain it through step 8.
- No new bytes, lifecycle state, or lock identity are required.
- A returned handle can continue ownership.
- A no-handle create can release after step 8.

Failure behavior is compatible with existing architecture:

- pre-rename lock/platform failure aborts creation before final visibility;
- rename failure is reconciled while ownership remains held;
- parent-sync failure cannot publish success;
- handle-construction failure uses normal failed-open cleanup;
- uncertain users or ownership use existing NONCONTINUABLE rules.

Candidate A alone is nevertheless incomplete because process termination releases the lock before namespace durability is necessarily known.

## 24. Candidate B assessment

No existing persisted field distinguishes:

- final root visible but not parent-durable;
- final root already durably published.

Control flags are explicitly zero in v1, and no creation-state slot, manifest bit, or surviving marker exists.

A new persistent marker could solve process-death adoption if:

1. the marker is durably present before rename;
2. parent `fsync` succeeds before clearing it;
3. marker clearing is itself durable;
4. an opener seeing the marker establishes parent durability before clearing it.

This is safe but introduces a new persistent state machine, compatibility rules, validation behavior, and recovery work. It is not minimal while Candidate D remains available.

## 25. Candidate C assessment

The stated Linux/POSIX model has separate events:

```text
rename -> runtime visibility
fsync(parent) -> crash durability
```

There is no architecture-defined primitive combining them into one indivisible event from other processes’ perspective. Candidate C would require external coordination—which reduces to a lock/marker design—or a publication redesign.

It is not viable within the frozen mechanism set.

## 26. Other viable candidate

A durable sidecar marker in the external parent is technically viable, but it would introduce:

- a new architecture-managed name;
- marker create/remove durability ordering;
- cleanup and unknown-entry rules;
- race-free inspection requirements;
- removal interaction.

It has more semantic surface than the recommended existing-lock plus adoption barrier.

## 27. Recommended semantic decision

### Invariant

> Ordinary database inspection, recovery, removal authority, READY publication, and acknowledged durable database work MUST NOT proceed while the final root’s external-parent entry lacks a successful synchronization ordered after its final rename.

### Ownership/gate mechanism

Use the existing:

- process-local stable root/control inode claim;
- exclusive `database.control` POSIX lock.

No parallel creator/remover lock authority is introduced.

### Acquisition point

After §4.7.8 step 6 successfully validates the complete staged bootstrap and before step 7 renames the root:

1. atomically establish the existing process-local inode claim;
2. acquire the ordinary nonblocking exclusive lock on staged `database.control`.

### Rename behavior

The directory rename preserves the root and control inodes, descriptor identity, process claim, and control lock. Final-path openers therefore contend on the same ordinary lock.

### Parent-fsync behavior

The creator retains ownership through successful external-parent `fsync`. The lock is coordination only; the `fsync` remains the durability mechanism.

### Release or continuation

- Returned handle: continue the same ownership into normal open/recovery/READY.
- No handle: release the lock and claim only after successful parent synchronization, then return success.

### Competing `OpenDatabase`

- While the creator lives and holds the publication gate: `DATABASE_BUSY`, before control-slot inspection, recovery, or mutation.
- After creator process death: the new owner may acquire the lock but must verify and synchronize the external-parent entry before control inspection/recovery/READY.

Because there is no marker, this adoption barrier must conservatively apply to every independent open.

### Removal interaction

A remover cannot acquire authority while the creator holds the publication gate. After owner death, a future D-M2 remover must establish or reconcile external-parent durability while holding the same lock before destructive use.

### Parent-fsync failure

No creation success or READY admission. Retain ownership while retrying/reconciling. If the creator dies, the next owner applies the same parent-durability adoption barrier.

### Creator crash

OS lock release does not prove publication. A surviving final root is validated and its external-parent entry synchronized by the next owner before use. A surviving staging root remains non-openable.

## 28–33. Architectural compatibility

28. **One-owner model:** Consistent. The creator becomes the single publication owner using the same claim and lock as every normal owner.

29. **Durable publication point:** Unchanged. It remains final-root rename followed by successful external-parent `fsync`.

30. **New persistent state:** None.

31. **New lifecycle state:** None. Private staging, publication ownership, and ordinary `OPENING/RECOVERING/READY` remain sufficient.

32. **New lock identity:** None. The lock remains the existing `database.control` inode.

33. **Ordinary OpenDatabase semantics:** The nonwaiting ownership result remains unchanged, but normal open gains one conservative requirement: after acquiring ownership and before database inspection, it must establish external-parent durability for the exact retained final-root entry. A failure is an existing I/O/durability open failure, not a new error category.

## 38. Constraints imposed on future D-M2

D-M2 remains free to define the removal protocol, but it must preserve these constraints:

- use the same process claim and `database.control` lock;
- never obtain removal authority while a creator owns root publication;
- after prior-owner death, establish or reconcile external-parent durability before destructive use;
- retain ownership through all acknowledged removal namespace operations;
- introduce no independent removal lock authority.
