# D-M2 semantic review

## 1. Verdict

**D-M2 — SINGLE CANONICAL REMOVAL PROTOCOL RECOMMENDED**

The canonical protocol should use:

> exclusive offline ownership, followed by an atomic no-replace rename of the live root to a recognized private retired-root name, external-parent `fsync`, and separately retryable private reclamation.

Durable removal means the captured old database identity no longer occupies final name `D`. Physical deletion of the retired tree is reclamation and may remain pending.

### 3. Exact semantic gaps

The current architecture leaves unspecified:

- whether the remover uses the process-local inode registry;
- what `CLOSED` means once the offline remover takes the lock;
- minimum destructive identity validation;
- damaged-database behavior;
- unknown-entry authority;
- recovery/catalog/WAL requirements;
- in-place versus retirement-rename deletion;
- control-file unlink timing;
- external-parent descriptor lifetime;
- durable removal publication point;
- success versus physical reclamation;
- retired-root naming and classification;
- parent-sync failure consequences;
- process/machine-crash prefixes;
- retry and recreation ordering.

### 4. Current preconditions

Currently explicit:

- removal is offline-only;
- no ordinary `DatabaseInstance` may be active;
- the database must be `CLOSED`;
- the remover must acquire the ordinary control-file lock.

Currently unspecified:

- process-local claim;
- minimum format validation;
- recovery;
- catalog interpretation;
- corrupt-database removal.

`CLOSED` should be understood as the pre-removal condition: no ordinary lifecycle owner, transaction, BufferPool, worker, or manager exists. The remover then acquires separate offline lifecycle authority without creating a READY `DatabaseInstance`.

### 5. Current ownership requirements

The same `database.control` lock is mandatory. The one-owner invariant also implies the same stable root/control-inode process claim, but §3.3.7 does not explicitly say so for removal.

No second lock authority is authorized.

### 6. Current durability requirements

Every acknowledged deletion requires its owning directory synchronization. The architecture does not currently identify the whole-root mutation or publication point.

## 7–11. Removal startup and validation

### 7. Removal versus normal open

Removal should use only ordinary open’s identity and ownership prefix:

```text
open parent/final root safely
    ->
claim stable root/control identity
    ->
acquire ordinary control lock
    ->
perform D-M1 parent-durability adoption
    ->
validate destructive authority
```

It should not perform:

- control-slot selection for recovery;
- WAL inventory;
- recovery;
- transaction-status reconstruction;
- catalog reconstruction;
- BufferPool construction;
- background-service startup;
- READY publication.

The database is being destroyed wholesale; logical consistency is not needed.

### 8. Minimum destructive validation

Before deleting or retiring anything, require:

1. final `D` is a directory opened no-follow relative to its retained external parent;
2. the parent entry still identifies the retained root inode;
3. `database.control` is a regular no-follow file;
4. the stable root/control-inode process claim succeeds;
5. the ordinary exclusive control lock succeeds;
6. D-M1’s external-parent adoption barrier succeeds;
7. control bytes establish the supported v1 DBlusBlus control-format family.

The last requirement need not establish a recovery-usable control generation. At least one slot should have exact `DBLUSCTL`, `format_version=1`, and recognized v1 framing. CRC/range corruption may then classify the target as a damaged but identifiable v1 database.

### 9. Corrupt-database removal

| Case | Recommended outcome |
|---|---|
| Valid v1 control, corrupt catalog | Removal allowed |
| Recognizable v1 control framing, corrupt control CRC/ranges | Removal allowed as damaged but identifiable v1 database |
| Missing required managed file | Removal allowed |
| Torn/malformed WAL | Removal allowed; WAL is not inspected |
| Unknown extra entry | Removal allowed under whole-root policy U1 |
| Malformed managed-looking filename | Treated as unknown root content |
| Unrelated directory | Refuse as `NOT_A_DATABASE` |

### 10. Missing or unrecognizable control

If `database.control` is:

- missing;
- a symlink or wrong type;
- unreadable;
- devoid of recognizable supported v1 family framing;

architecture-managed removal must refuse. It cannot safely prove that the caller selected a DBlusBlus database rather than an unrelated directory.

Manual/external filesystem removal remains outside this protocol.

### 11. Unsupported future format

An exact control-family magic with an unsupported future format version must return `UNSUPPORTED_DATABASE_FORMAT`.

V1 must not recursively destroy a future-format database whose namespace and ownership rules it cannot interpret. No force-removal API is assumed.

## 12–13. Unknown entries

### 12. Candidate analysis

| Policy | Benefit | Risk | Assessment |
|---|---|---|---|
| U1: explicit whole-root authority covers all contents | Makes whole-root removal complete; catalog/recovery unnecessary | Could delete user-added material inside an explicitly targeted DB root | Preferred with strong root validation and no-follow containment |
| U2: unknown entries block removal | Maximally preserves external material | One unknown file can permanently prevent whole-root removal and reclamation | Safe but inconsistent with supported whole-root destruction |
| Ordinary orphan rule | Deletes only proven managed orphans | Does not authorize deleting the root itself | Not sufficient |

### 13. Recommended policy

**POLICY U1**

> After the remover has proved supported-v1 root identity and acquired exclusive whole-root authority, explicit whole-database removal covers every entry beneath that retained root. Traversal must remain no-follow, descriptor-relative, and contained within that root.

This does not weaken ordinary orphan cleanup:

- ordinary orphan cleanup still never deletes unknown names;
- only explicit whole-root destruction gains U1 authority;
- unrelated external-parent siblings remain untouched;
- mount/cross-filesystem traversal must be rejected rather than followed.

## 14–17. Removal-unit candidates

### 14. In-place deletion

In-place deletion is not recommended.

Fatal weaknesses:

- a crash leaves a partly deleted database at live name `D`;
- later open sees corruption rather than a classified removal state;
- retry may depend on files already deleted;
- `database.control` must eventually be unlinked while `D` still exists;
- after control unlink, a process crash leaves no ordinary lock path or reliable identity proof;
- replacement of `database.control` could create an independently lockable inode while old `D` remains;
- final `rmdir` and parent `fsync` cannot be atomic with control unlink.

#### In-place failure matrix

| Failure boundary | Namespace | Durable state | Lock | Result | Retry | Open `D` | Create `D` |
|---|---|---|---|---|---|---|---|
| Before content deletion | Complete `D` | Live DB | Held | Failure | Safe | Busy, then normal | Fails because `D` exists |
| During content deletion, control retained | Partial `D` | Arbitrary partial prefix | Held until crash | Failure | Possible but corruption-sensitive | Busy; after crash corrupt | Fails |
| After control unlink, before root removal | Partial `D`, no control path | Unsafe/ambiguous | Lock only on unlinked inode | Failure | Cannot safely reacquire identity | Not a database | Fails while `D` exists |
| After root `rmdir`, before parent sync | `D` runtime-absent | May reappear partially | Old lock inode detached | Failure | Ambiguous | Missing or corrupt after crash | Race-prone |
| After parent sync | `D` absent | Durable absence | Releasable | Success | N/A | Missing | Allowed |

### 15. Atomic root retirement

Root retirement is recommended:

```text
D
    ->
D.dblusblus-removing-<token>
```

Benefits:

- no database content is deleted while `D` is live;
- runtime disappearance is one atomic rename;
- one external-parent `fsync` durably establishes both absence of `D` and presence of the retired root;
- `database.control` remains the same inode and lock object;
- crash prefixes contain either a complete live root or a complete retired root;
- private cleanup cannot expose a half-database as `D`;
- physical reclamation can retry independently.

#### Root-retirement failure matrix

| Failure boundary | Namespace | Durable state | Lock | Result | Retry | Open `D` | Create `D` |
|---|---|---|---|---|---|---|---|
| Before rename | Complete `D` | Live | Held | Failure | Retry removal | Busy, then normal | Fails |
| Rename succeeded, parent sync pending | Retired name visible; `D` absent at runtime | Publication uncertain | Held | No success | Retry/reconcile parent | Missing at runtime; may return after crash | Must establish old absence before publishing new `D` |
| Parent sync succeeded | Retired name durable; `D` durably absent | Removal published | Held | Semantic success established | Cleanup retryable | Missing or newly recreated DB | Allowed |
| During private cleanup | Partial retired tree | `D` remains durably absent | Retain while active | Still semantic success | Idempotent cleanup | Cannot reach old root through `D` | Allowed |
| Retired `rmdir` before final parent sync | Retired name runtime-absent | Residue absence uncertain | Held if process alive | Semantic removal remains success | Retry if name reappears | No old `D` | Allowed |
| Final parent sync | Neither old `D` nor retired name | Complete physical reclamation | Releasable | Success | Complete | Missing/new DB only | Allowed |

### 16. Other viable candidate

A persistent removal marker inside live `D` could make in-place deletion retryable, but it would add:

- a new persistent state;
- control/format compatibility rules;
- open-time marker dispatch;
- more crash transitions.

It is inferior to a namespace-only retirement rename.

### 17. Candidate comparison

| Property | In-place deletion | Root retirement |
|---|---|---|
| One-owner compatibility | Initially yes | Yes |
| New persistent format | None, but safely finishing likely needs marker state | None |
| New namespace state | No distinct safe state | One recognized retired-root grammar |
| Unknown contents | Can block late root removal | Moved privately before cleanup |
| Runtime atomicity | No | Yes |
| Crash classification | Partial live DB possible | Complete live or complete retired root |
| Retryability | Loses control identity late | Deterministic |
| Control-lock continuity | Unsafe near control unlink | Preserved across root rename |
| External-parent durability | Only at very end | Defines semantic removal |
| Partial cleanup visibility | Under live `D` | Private only |
| Recreate before cleanup | Unsafe | Safe after retirement publication |
| Semantic complexity | High and fragile | Small, aligned with object retirement |
| Verdict | Reject | Adopt |

## 18. Recommended canonical protocol

| Stage | Required action |
|---|---|
| **Precondition** | No ordinary `DatabaseInstance` exists; database is offline/CLOSED; no transactions, workers, BufferPool, managers, or background producers remain. |
| **Root open** | Open retained external-parent and exact final `D` descriptors with no-follow/type checks. |
| **Claim** | Atomically claim the stable root/control inode identity in the existing process-local registry. |
| **Lock** | Open `database.control` and acquire the ordinary nonblocking exclusive lock. Contention returns `DATABASE_BUSY` before inspection or mutation. |
| **D-M1 adoption** | Verify that external-parent entry `D` still identifies the retained root, successfully `fsync` the parent, and reconcile identity before reading control or mutating namespace. |
| **Validation** | Establish supported-v1 DBlusBlus root identity using control-family magic/version/framing. Full slot selection, WAL, recovery, catalog, and READY validation are unnecessary. |
| **Retired-name selection** | Generate an exact reserved sibling name `D.dblusblus-removing-<token>`, require destination absence, and retry token selection on collision. |
| **Live-root retirement** | Same-filesystem no-replace rename `D` to the selected retired name. Do not delete any internal content before retirement durability. |
| **Parent fsync** | `fsync` the external parent after rename. Reconcile uncertain rename/sync outcomes under §4.7.2. |
| **Durable publication** | Successful parent sync is the linearization point: captured old root identity is no longer the live database named `D`, and the private retired name is durable. |
| **Cleanup** | The remover may synchronously traverse the retired root no-follow and bottom-up. It may delete managed and unknown contents under U1. |
| **Retired-root removal** | Keep `database.control` until late cleanup when practical; after the tree is empty, remove the retired root with `rmdir`. |
| **Final sync** | Synchronize every internal directory whose deletions are claimed complete, then `fsync` the external parent after retired-root `rmdir`. |
| **Ownership release** | If cleanup is deferred or fails, stop using the retired root, release the old control lock while retaining the process claim, close it, then remove the claim. If cleanup completes, release after final parent sync. |
| **Result** | Return semantic removal success once retirement rename plus external-parent `fsync` succeeded. Private cleanup failure does not reverse success. |

No recovery, catalog decoding, or READY state is entered.

## 19–24. Ownership and races

### 19. `database.control` lock lifetime

The lock is acquired before destructive validation and held through:

- D-M1 adoption;
- identity validation;
- retirement rename;
- external-parent `fsync`;
- removal publication.

If immediate cleanup is attempted, retaining it through cleanup is preferred. It may be released after durable retirement if cleanup is deferred because the old root is no longer a live database target.

### 20. Split-lock-inode risk

The protocol must never unlink or replace `database.control` while old `D` remains live.

After durable root retirement:

- old `D` is absent;
- the old control inode belongs only to the private retired root;
- a recreated `D` is a distinct database with a distinct control inode;
- deleting old control no longer creates two lock identities for one live root.

### 21. Open race

- Before rename: opener reaches the same control inode and receives `DATABASE_BUSY`.
- After runtime rename: `D` is absent, so open cannot attach to the old root.
- After durable publication: open sees no `D`, or a newly created distinct database.
- Retired-root names are never valid `OpenDatabase` targets.

### 22. Create race

Before runtime retirement, `D` exists and create fails its absent-root precondition.

After runtime retirement but before remover parent sync, a new creator must not publish a new `D` until it has successfully synchronized the external parent and thereby established the old root’s absence. Its own final rename remains followed by the normal creation parent-sync barrier.

After durable retirement, recreation may proceed even if private cleanup remains.

A removal result applies to the captured old root identity. A separately created new `D` may exist by the time removal returns.

### 23. Same-process race

The remover holds the existing stable root/control-inode process claim. A same-process open/removal of that old root receives `DATABASE_BUSY`, including through an alternate spelling.

The claim follows the old root inode across retirement rename and is removed only after lock release.

### 24. Alias assessment

Aliases that resolve to the same managed final entry/inode contend through the stable claim and control lock before retirement. After retirement, the managed final entry no longer reaches the old root.

External bind mounts or unmanaged secondary namespace attachments are outside the managed no-follow root contract and must not be traversed during cleanup.

## 25–28. Recommended invariants

### 25. Removal publication invariant

> Whole-database removal is durably published only after the captured live final root has been renamed without replacement to its exact private retired-root name and the external parent directory has been successfully synchronized after that rename.

### 26. Unknown-entry invariant

> Ordinary orphan cleanup never deletes unknown entries. Explicit whole-database removal of a validated, exclusively owned supported-v1 root authorizes deletion of all entries beneath that retained root, but traversal never follows symlinks, crosses an unproven filesystem/mount boundary, or touches external-parent siblings.

### 27. Crash invariant

> Every removal crash prefix leaves the old identity as either a complete live `D`, a complete or partially reclaimed recognized private retired root, or durably absent. Internal deletion never starts until the retired-root rename is parent-durable.

### 28. Control-lock invariant

> No step may leave old `D` representing the database while its ordinary control lock inode has been unlinked, replaced, or made independently recreatable. Control deletion is legal only after durable retirement of old `D`.

## 29–32. Result semantics

### 29. Success

`RemoveDatabase` success means:

- the captured old database identity no longer occupies live final name `D`;
- that absence and the retired private name were durably published.

It does not require every old byte to have been reclaimed.

### 30. Failure before publication

Before successful retirement parent sync:

- no success is reported;
- if rename has not occurred, complete `D` remains authoritative;
- if rename occurred but sync failed, publication outcome is uncertain;
- the remover retains ownership while retrying/reconciling;
- if it safely unwinds, it returns existing I/O/durability failure;
- the next actor classifies `D` versus the retired name and continues accordingly.

No internal content deletion may have begun.

### 31. Failure after publication

After successful retirement parent sync:

- old `D` remains semantically removed;
- the retired tree remains cleanup state;
- no later local failure may rename it back or report the old database as live;
- recreation of `D` is allowed.

### 32. Cleanup failure

Cleanup failure after publication does not change semantic removal success.

The result should remain successful removal with cleanup residue recorded diagnostically or exposed as cleanup-pending state. It must not be reported in a way that implies old `D` remains live.

No background cleanup promise is introduced.

## 34. Machine-crash matrix

| Machine-crash point | Permitted durable survivor | Classification |
|---|---|---|
| Before retirement rename | Complete live `D` | Removal not published |
| After rename, before parent sync | Live `D` or private retired root according to surviving rename prefix | Retry removal or establish retired publication |
| After retirement parent sync | Private retired root | Old `D` durably absent |

## 35. Parent-fsync failure

If retirement rename succeeds but external-parent `fsync` fails:

- `D` may be runtime-absent;
- the retired name may be visible;
- durable outcome is uncertain;
- removal success is forbidden;
- internal cleanup is forbidden;
- the remover retains ownership while retrying/reconciling;
- safe unwind returns `IO_OR_DURABILITY_FAILURE`;
- a later actor must synchronize/reconcile the external parent before acting on absence.

## 36. Retry and idempotence

The namespace protocol is internally idempotent:

- live `D`: retry ownership and retirement;
- recognized retired root: complete publication if necessary, then retry cleanup;
- retired root partially cleaned: repeat no-follow bottom-up traversal;
- retired root absent after durable cleanup: complete.

A fresh API call finding no final `D` may use the existing missing/`NOT_A_DATABASE` result rather than pretending it captured an identifiable database. No new API result is required.

## 37–40. Retired-root namespace

### 37. Naming recommendation

Use:

```text
D.dblusblus-removing-<token>
```

where `<token>` is exactly 32 lowercase hexadecimal digits representing a collision-resistant 128-bit token.

Requirements:

- same external parent as `D`;
- destination-absent/no-replace rename;
- collision causes new token selection;
- this grammar is reserved and never an ordinary database target;
- `D.dblusblus-creating` and removal-retired names remain distinct.

The randomness source and retry implementation are implementation freedom.

### 38. Ownership and cleanup

The remover owns the retired root while its claim/lock remains active. Later cleanup may be performed by:

- the same removal call;
- a later explicit namespace-maintenance invocation;
- an optional create/removal maintenance opportunity.

No global background daemon is required.

Cleanup targets only exact reserved retired-root names and remains descriptor-relative. If control remains, cleanup should acquire its ordinary lock. If prior cleanup already removed control, exact retired-name classification and idempotent descriptor-contained cleanup govern the residue.

Duplicate cleanup attempts must be serialized per artifact or tolerate exact `ENOENT`/already-removed races without leaving the retained root.

### 39. Recreation while retired root remains

Allowed after durable retirement publication.

A new `D` has:

- a new root inode;
- a new `database.control` inode;
- a separate ownership domain.

Cleanup remains bound to the old retired-root descriptor/name and must never resolve through new `D`.

### 40. FileId and database-local identity

FileIds are database-local. Old and new databases at the same final pathname may reuse the same numeric FileIds without collision because their root/control ownership domains are distinct.

No global database UUID exists or is needed for this protocol.

## 41–46. Subsystem decisions and errors

### 41. Recovery before removal

**Not required.**

Recovery would add WAL, status, catalog, BufferPool, and failure complexity without improving whole-root destruction. Exclusive ownership plus supported-format root identity is sufficient.

### 42. Catalog dependency

**Not required.**

The remover does not classify files as committed/orphaned individually. U1 authorizes destruction of the validated root as a unit.

### 43. WAL, pending, and system files

After durable root retirement:

- `wal/` segments need no inspection or retention-floor proof;
- `pending/` entries need no transaction/orphan proof;
- catalog/status/system files need no semantic teardown;
- all are private reclamation content.

For physically complete cleanup:

1. traverse directories no-follow;
2. remove children bottom-up;
3. synchronize each directory whose child deletions are claimed complete;
4. remove subdirectories and synchronize their parent;
5. remove root-level files, preferably keeping control until late;
6. `rmdir` the retired root;
7. `fsync` the external parent.

### 44. Symlink and special-object safety

- Symlink: unlink the symlink entry itself; never follow it.
- FIFO/socket/device: unlink only its retained-root entry.
- Directory: open no-follow and recurse descriptor-relative.
- Mount/cross-filesystem boundary: do not traverse; leave cleanup pending or fail that reclamation attempt.
- Root/control wrong type: refuse destructive authority.
- External-parent siblings: never touched.

### 45. Future-format decision

Recognizable future format: refuse with `UNSUPPORTED_DATABASE_FORMAT`.

Supported-v1 framing with corruption: removable.

Unrecognizable or missing control: refuse as non-database/I/O failure.

### 46. Error categories

| Condition | Result |
|---|---|
| Owner contention | `DATABASE_BUSY` |
| Missing/unrecognizable root | `NOT_A_DATABASE` or existing missing-target equivalent |
| Unsupported future control format | `UNSUPPORTED_DATABASE_FORMAT` |
| Recognizable supported-v1 corruption | Removal may proceed |
| Parent/open/rename/sync failure before publication | `IO_OR_DURABILITY_FAILURE` |
| Publication succeeded, cleanup failed | Semantic success; cleanup remains pending |
| Ownership/cleanup cannot be safely quiesced | Retain authority until safe unwind/process exit; no false success before publication |

No new named error is necessary.

## 52. D-M1/D-M2 integration points

The combined architecture patch should encode:

1. creator, opener, and remover use one root/control-inode claim and lock authority;
2. creator takes it before final-root rename;
3. independent opener/remover performs external-parent adoption after ownership;
4. remover retires only an adopted exact final root;
5. recreation establishes prior final-name absence before publishing a new root;
6. all root create/remove publication points use the external-parent descriptor and `fsync`;
7. no new lifecycle state, control bit, or lock file is introduced.
