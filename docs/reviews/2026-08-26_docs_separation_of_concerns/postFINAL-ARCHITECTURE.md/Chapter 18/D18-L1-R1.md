## 9–24. D18-L1 final contract

9. Every front-end attempt has one conceptual backing owner covering original source and referenced derived payload.
10. Original source bytes remain immutable while borrowed.
11. Tokens and later objects may borrow source or derived payload.
12. Before releasing backing, borrowers must either retain the owner or materialize/transfer required data.
13. Decoded string bytes remain valid for every consumer lifetime.
14. Decoded quoted-identifier bytes remain valid and exact.
15. Canonicalized unquoted-identifier bytes remain valid.
16. Lossless numeric provenance remains available through Chapter-17 classification.
17. Tokens may be destroyed after parsing once dependent payload has been transferred or no longer remains referenced.
18. Raw AST may be released after binding when no bound object, diagnostic, or result depends on it.
19. Bound objects may borrow source/raw-AST data only while backing remains alive; otherwise binding materializes it.
20. `SourceSpan` is exactly `[start_byte_offset, end_byte_offset)` over the original request, with `0 <= start <= end <= source_byte_length`.
21. Span values may outlive source bytes; dereferencing them requires retained source or materialized text.
22. Diagnostics need not retain complete SQL text indefinitely, but required rendered text must be materialized before source release.
23. Source, payload backing, spans, and raw SQL are runtime-only and introduce no persistence.
24. Allocation, ownership, and container representation remain implementation-defined.

The pre-existing arena requirement in §18.14 directly contradicted D18-L1 and was minimally synchronized: arena ownership is now permitted, not required. The broader F18-N2 cleanup remains pending.

## 25–38. D18-R1 final contract

25. Chapter 18 defines no implementation-convenience SQL-language maxima for source/token lengths, nesting, lists, statement count, or AST size/depth.
26. Finite operational memory, work, nesting, stack-safety, and node budgets are permitted but remain runtime policy, not grammar.
27. `FrontEndResourceLimit` means deliberate refusal at a configured or safety guard.
28. `OutOfMemory` means inability to satisfy a required allocation, including during lexing, parsing, decoding, AST construction, or binding.
29. The categories are distinct: checked-budget refusal versus allocation failure.
30. Validity and processability are separate; the same valid SQL may succeed under one configuration and resource-fail under another.
31. Stack overflow, undefined behavior, memory corruption, uncaught allocation failure, and parser-depth process abort are nonconforming outcomes.
32. Resource failure exposes no successful partial token stream or raw AST.
33. Resource pressure cannot authorize truncation, prefix processing, child removal, deduplication, reordering, or approximate literal handling.
34. Private lexer/parser/binder and backing state must unwind safely.
35. §39.1 retains transaction-state ownership; Chapter 18 adds no transaction state, physical undo, or retry rule.
36. Batch parsing cannot fabricate success for a completed prefix after resource failure.
37. Resource budgets and failed front-end state are not persisted or recovered.
38. Budget decomposition and numerical values remain configuration/implementation choices.

| Raw AST | May borrow or own | Through all raw-AST consumers |
| Bound object | May borrow only with retained owner | Through all bound consumers |
| `SourceSpan` | Offset value only | May outlive source; dereference may not |
