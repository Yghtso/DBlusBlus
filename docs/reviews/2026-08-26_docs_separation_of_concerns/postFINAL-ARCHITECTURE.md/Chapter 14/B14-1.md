4. **Original B14-1 failure:** A write-capable transaction without a registered SQL snapshot could remain active while the status cutoff advanced past its TxnId, then later persist that retired TxnId in `xmin` or `xmax`.

5. **Final D14-M1 rule:** Every write-capable normal transaction registers a dependency protecting its own TxnId as an indivisible part of transaction registration. Cutoff publication cannot retire that TxnId until C5/A3 releases the dependency.

6. **Canonical terminology:** `write-status dependency`.

7. **Write-capable classification:** Ordinary transactions are write-capable unless explicitly established as read-only at registration. Merely not having written yet does not make one read-only.

8. **Read-only classification:** Explicitly read-only is immutable, cannot publish persistent self-TxnId correctness metadata, cannot be silently upgraded, and may omit the write-status dependency.

## Registration and cutoff ordering

9. **Registration point:** TxnId assignment, active-registry registration, and write-status-dependency registration form one conceptual transaction-registration publication.

10. **Cutoff linearization:** Transaction registration and cutoff candidate calculation/publication have a gap-free ordering in the shared status-history coordination domain.

11. **Assignment-to-registration race:** Eliminated. A write-capable transaction is never admitted with an assigned-but-unregistered TxnId.

12. **Reclaimer-first race:** If cutoff `C` publishes first, the later transaction receives `T >= C` and registers its dependency before admission.

13. **Transaction-first race:** If transaction `T` registers first, its dependency prevents the cutoff from retiring `T`.

14. **Cutoff constraint:** The reclaimer chooses the greatest legal cutoff that does not retire any registered write-capable transaction’s TxnId and satisfies all other bounds.

15. **Page alignment:** Unchanged. The selected cutoff remains page-aligned under existing status-page arithmetic.

16. **Exclusive boundary:** Unchanged; `T < txn_status_reclaim_before` is retired.

Race summary:

| Case | Result |
|---|---|
| Write-capable `T` registers first | Cutoff cannot retire `T` |
| Cutoff `C` publishes first | New `T >= C`; dependency registered before admission |
| Idle RC write-capable transaction | Own status remains pinned without a SQL snapshot |
| Explicitly read-only transaction | No D14-M1 pin; persistent self-TxnId writes forbidden |
| C4 complete, C5 pending | Dependency remains registered |
| C5/A3 complete | Future-publication blocker clears; existing metadata may still pin status |

## Mechanism separation

17. **READ COMMITTED:** A write-capable transaction remains continuously protected between statements even when no SQL snapshot is registered.

18. **REPEATABLE READ:** Its retained SQL snapshot and write-status dependency remain independent claims and may impose different bounds.

19. **SQL snapshot:** Protects logical visibility history; `global_oldest_snapshot_xmin` is unchanged.

20. **Read epoch:** Continues to protect physical RID identity only. No D14-M3 behavior was added.

21. **StatusHistoryGuard:** Remains a bounded maintenance status-range claim and does not substitute for the transaction-lifetime dependency.

## Transaction lifetime

22. **ACTIVE:** Dependency retained.

23. **MUST_ABORT:** Dependency retained through ordinary abort cleanup.

24. **COMMITTING:** Dependency retained.

25. **ABORTING:** Dependency retained.

26. **C4/C5:** C4 terminal publication does not release the dependency; C5 releases it with other transaction resources.

27. **A2/A3:** A2 terminal publication does not release the dependency; A3 releases it.

28. **After release:** Existing tuple/catalog references remain ordinary persistent status dependencies until freezing, normalization, physical removal, or another authorized status-independent rewrite eliminates them.

29. **Future publication after release:** Forbidden.
