## Canonical affected-row semantics

The count is:

- statement-scoped runtime result metadata;
- owned only by the final successful execution attempt;
- reset to zero for every replacement attempt;
- never accumulated across retries;
- independent of candidate visits, tuple versions, indexes, WAL records, page mutations, or diagnostic counters.

A failed statement returns its canonical error and no successful or partial affected-row count.

### Retry behavior

[§15.7.1](/home/yghtso/Projects/DBlusBlus/docs/ARCHITECTURE.md:12378) now explicitly discards provisional counting during clean READ COMMITTED retry.

- Abandoned RC attempt: contributes zero.
- Replacement RC attempt: fresh snapshot, same CommandId, count starts at zero.
- Retained transaction-duration locks carry no count contribution.
- RR snapshot, serialization, and retry rules remain unchanged.

## Operation-specific rules

### INSERT

[INSERT counting](/home/yghtso/Projects/DBlusBlus/docs/ARCHITECTURE.md:12177):

- Each successfully inserted logical input row in the final attempt counts once.
- Single-row success: `1`.
- Successful `N`-row INSERT: `N`.
- Heap tuple plus multiple indexes still counts as one per input row.
- Failed INSERT publishes no successful count, including failures after partial physical publication.

### UPDATE

[UPDATE counting](/home/yghtso/Projects/DBlusBlus/docs/ARCHITECTURE.md:12238):

- Each distinct finalized target that survives locking, revalidation, current-owner handling, and predicate qualification counts once.
- Old-version mutation plus replacement version counts as one.
- Index and WAL activity do not multiply the count.
- A qualifying `SET x=x` target counts once.
- An otherwise legal physical no-op optimization cannot change the count and is not authorized merely by this rule.
- Stale or nonqualifying targets contribute zero.
- Chapter 31’s finalized target spool prevents duplicate RID production from double counting.

### DELETE

[DELETE counting](/home/yghtso/Projects/DBlusBlus/docs/ARCHITECTURE.md:12275):

- Each distinct finalized target receiving the successful logical delete counts once.
- Candidate discovery, `xmax/cmax`, index policy, WAL, and page mutations do not define the count.
- A stale/nonqualifying target contributes zero.
- Successful UPDATE or DELETE with no qualifying finalized target reports `0`.

## Multirow and failure semantics

A successful multirow statement reports the operation-specific logical cardinality from its final attempt.

If rows 1–7 have physical mutations and row 8 causes mandatory abort:

- statement result: canonical error;
- transaction: `MUST_ABORT -> ABORTING -> ABORTED`;
- successful affected-row count: none, not `7`;
- physical effects: aborted MVCC garbage under existing no-user-DML-undo rules.

The same no-count rule applies to:

- recoverable statement failure;
- mandatory-abort failure;
- deadlock victimization;
- RR serialization failure;
- uniqueness, NOT NULL, CHECK, expression, or type failure;
- database-noncontinuable outcome.

Existing failure classifications remain unchanged.

## Publication semantics

Affected-row count and `RETURNING` share the existing successful statement-result envelope.

Explicit transaction:

- Count may publish after canonical statement success.
- Transaction remains `ACTIVE`.
- Later COMMIT or ROLLBACK is separate.
- Later rollback does not retroactively rewrite the earlier result.
- The count never implied durable COMMIT.

Autocommit:

- Count remains request-owned and hidden through implicit COMMIT C4–C5.
- Commit failure before successful response publication withholds the successful count.
- Successful response publishes the final count without recounting rows.
- Count and RETURNING cannot use contradictory publication boundaries.

## Persistence and recovery

Affected-row count is not:

- WAL-logged;
- checkpointed;
- stored in `database.control`;
- stored in TxnStatus or catalogs;
- reconstructed or replayed during recovery.

No result width, persistent integer format, new WAL record, or result-recovery protocol was introduced.

## Exact cases

| Case | Result |
|---|---:|
| Single-row INSERT succeeds | `1` |
| Five-row INSERT succeeds | `5` |
| UPDATE final attempt has eight finalized targets | `8` |
| `SET x=x` matches six finalized targets | `6` |
| DELETE final attempt deletes four targets | `4` |
| Successful UPDATE has no finalized target | `0` |
| Retry sees 5, final attempt updates 3 | `3` |
| Retry sees 4, final attempt sees none | `0` |
| Provisional count 2 then fatal failure | error, no count |
| Same target produced repeatedly but finalized once | `1` |
| Stale target not acted upon by final attempt | `0` |
| Seven rows published before row-eight mandatory abort | error, no count |
| Autocommit provisional result 7, COMMIT fails | commit/error result, no `7` |
| Autocommit DELETE 4, COMMIT succeeds | `4` |
| Explicit UPDATE reports N, later transaction aborts | earlier result remains `N` |

Separate SQL statements may each count the same logical row once; there is no transaction-wide deduplication.
